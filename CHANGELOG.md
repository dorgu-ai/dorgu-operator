## [Unreleased]

## [0.13.0] - 2026-11-09

The operator half of the Dorgu CP1 release, paired with CLI v0.14.0 (the harness: a gate every proposal and approval passes through, an apply ticket, verification and rollback that hold, and a KPI report).

### Migration checklist (read this first)

1. **Upgrade the CLI to v0.14.0 first, then the operator.** A CLI older than v0.14.0 ignores apply tickets and patches the Deployment from `spec.steps[]` with none of the new checks; the operator cannot stop it. v0.14.0 against an older operator is safe (it refuses and says why).
2. **Apply the CRDs before the operator starts.** Helm does not upgrade CRDs: `kubectl apply -f charts/dorgu-operator/crds/` (or reinstall). New fields: `status.gate`, `status.applyTicket` (with `issuedAt`, `observedGeneration`), the `Ticketed` and `Expired` phases, and a DNS-1123 label pattern on `ClusterPersona ... excludeNamespaces`.
3. **`RemediationAction.spec.action` is deprecated.** It is now a notification with no patch (`{type: notification}`); `spec.steps[]` is the only plan. Anything that read the patch from `spec.action` must read `spec.steps[]`.
4. **New phases and reasons:** `Ticketed` is new (approved, gate re-run, ticket issued). `Expired` is now actually reached, for a proposal nobody approved within `remediation.pendingTTL` (default 24h) or one superseded by a worse incident (condition reason `Superseded`; the other is `ApprovalTimedOut`). A tool that switched on `phase` must handle both.
5. **New flags and Helm values.** From B7: `--enable-event-pipeline` / `eventPipeline.enabled` (default off). From B9: `--readiness-threshold` / `healthCheck.readinessThreshold`, `--liveness-restart-count` and `--liveness-restart-window` / `healthCheck.livenessRestarts.count` and `.window`, `--incident-recurrence-cap` and `--incident-recurrence-window` / `healthCheck.recurrence.cap` and `.window`, `--resolved-incident-retention` / `healthCheck.resolvedRetention`. From B4/B2: `--llm-cache-ttl` / `llm.cacheTTL`, `--remediation-pending-ttl` / `remediation.pendingTTL`.
6. **RBAC: the ClusterRole gains `delete` on `incidentmemories.dorgu.io` (pruning of old Resolved incidents), nothing else.** The operator still has no write verbs on Deployments and no read on Secrets. If you manage the ClusterRole yourself, add the verb or pruning fails.
7. **The event pipeline is off by default and the WebSocket server is removed.** `--enable-websocket`, `--websocket-addr` and the `websocket.*` values are gone (the flags stop the operator at startup; old values files still install). The Kubernetes-Event watcher and DorguEvent writer only run with `eventPipeline.enabled=true`.
8. **`dorgu remediation reject --reason` changed (CLI).** It takes a fixed list (`wrong-diagnosis`, `too-risky`, `not-now`, `duplicate`, `not-needed`, `other`; `other` needs `--note`) and is recorded as a `RejectionReason` condition. Free text is now an error.
9. **`helm upgrade --reuse-values` from 0.12.x works.** The chart reads every key added since 0.12.1 (`healthCheck.readinessThreshold`, `healthCheck.livenessRestarts.*`, `healthCheck.recurrence.*`, `healthCheck.resolvedRetention`, `remediation.pendingTTL`, `eventPipeline.enabled`, `llm.cacheTTL`) with a built-in default, because `--reuse-values` ignores the new chart's `values.yaml`. Before this fix the render failed with a nil-pointer error on `eventPipeline` (or an empty flag value), so the upgrade stopped. Apply the CRDs first as above.
10. **Pending RemediationActions created by 0.12.x cannot be approved after the upgrade, and expire.** A proposal made by the old operator has no `status.gate` record, so approving one is refused (`NoProposalRecord`, CLI exit 4). It now ends `Expired` with the condition reason `PredatesGate` (terminal, nothing applied, not a failure and not a rejection: no failed-remediation cooldown), and the operator proposes again on the next cycle. You can also delete them first (`kubectl delete remediationactions -A --all`, or only the `Pending` ones) or leave them to expire. (EKS QA 2026-11-09, F-3.)
11. **A crash loop, a not-Ready container or a liveness kill gets an advisory proposal again.** The AI planner's plan for these usually mixes a memory raise with advice. The gate refuses a persona change the rules did not recommend (`Validate/ActionClass`), and 0.13.0 used to refuse the whole plan, leaving an incident with a diagnosis and no proposal. The persona-update steps are now dropped and the plan's advisory steps are proposed as a `notification` action, through the gate like any plan; the refusal of the first plan is still recorded (a `DorguValidateRefused` Event on the incident, `dorgu_gate_decisions_total{stage="Validate",result="refuse",reason="action-class"}`). The model is asked once (its answer is cached), and the proposal is deduplicated like any other. A plan with nothing advisory in it stays refused. (EKS QA F-5.)
12. **What a rollback does and does not touch.** A rollback (a verification that finds the workload still unhealthy, `RolledBack`) **restores the ApplicationPersona fields Dorgu changed, and only those that still hold what Dorgu wrote**; a field a person changed after the heal is left alone and named (`PersonaEditedSinceHeal`). It **never touches the Deployment**: the operator has no write verbs on workloads. So after a heal that was applied with `dorgu remediation approve` or `heal`, the Deployment still carries the new resources, the incident outcome is `partial`, and the RemediationAction says so (`WorkloadDiverged=True`, with each field, its value now and before, and the `kubectl set resources` command that finishes the rollback). If the workload was never patched (an approval with `--no-heal`), `WorkloadDiverged=False/WorkloadRestored` says nothing was left to undo. A ticketed `dorgu remediation rollback` that reverts the workload with your credentials is planned for P2. KPI I4 is worded accordingly: the persona is restored, and the workload outcome is stated truthfully.
13. **Behaviour changes you will notice:** pod incidents for not-Ready and liveness-restarting containers (new signals); a recurrence after Resolved opens a new incident (`-r1`, `-r2`) instead of folding silently; one OOM is one incident; the gate refuses (and persists the reason) where the proposer used to skip; AI calls are cached per situation.

Known gaps at this release are listed under "Known gaps" below: CPU throttling (P2), status-RBAC ticket forgery (P2 task 2.5), user-writable annotations (P2 task 2.5), identity scenarios ID-01 to ID-04 (CP2).

### Upgrade notes

> **The WebSocket server is removed, with its flags and Helm values (harness P1 B7, finding F-5).** `--enable-websocket` and `--websocket-addr` are gone (passing either now stops the operator at startup with "flag provided but not defined"), and so are the Helm values `websocket.enabled`, `websocket.port`, `websocket.service.type` and `websocket.service.port`, the `<release>-websocket` Service and the container's `websocket` port. The server was unauthenticated (`CheckOrigin` always true) and nothing used it: the CLI removed its client in v0.13.0 and the dashboard uses SSE. **Old values files still install**: Helm ignores unknown keys, so a `values.yaml` that still sets `websocket.*` renders the same chart as one that does not, and a `--set websocket.enabled=true` is a harmless no-op. If you ran a `kubectl port-forward svc/<release>-websocket 9090:9090`, it has nothing to forward to; follow changes with `kubectl get incidentmemories,remediationactions -A -w`. No NetworkPolicy shipped with the chart referenced port 9090, so there is nothing to remove there; remove your own.
>
> **The event pipeline is off by default (task 1.15).** The Kubernetes-Event watcher and the DorguEvent cleaner are no longer started, and the health cycle no longer writes a DorguEvent per contributing signal, because nothing reads those records. Turn it back on with `--enable-event-pipeline` / Helm `eventPipeline.enabled=true`; `dorguEvents.retention` and `dorguEvents.maxRecords` (and `--dorgu-event-retention`, `--dorgu-event-max-records`) apply only then, and the chart renders them only then. Existing DorguEvent records are not deleted; with the pipeline off nothing prunes them, so delete them (`kubectl delete dorguevents -A --all`) or run once with the pipeline on. The Kubernetes Events posted on incidents (`kubectl describe`) are unchanged and always on.
>
> **Pod detection now skips the same namespaces the gate refuses (finding F-13).** It used to skip only `kube-system`. It now also skips the operator's own namespace, `safety.excludedNamespaces` (`--safety-excluded-namespaces`) and every ClusterPersona `spec.policies.selfHealing.excludeNamespaces` entry, compared trimmed and lowercased like the gate does. A pod failing in one of those namespaces raises **no incident at all**, where before it raised one that was recorded but never remediated. If you relied on seeing incidents for a namespace you excluded, remove it from `excludeNamespaces`. If the ClusterPersona list cannot be read, the pod collector fails (it does not guess), so the cycle resolves no incident and the verifier reports `Unknown`, exactly as for any other failed collector.
>
> **One OOM is now one incident (finding F-9).** A pod that is OOM-killed and then crash-loops used to raise two incidents (`health/CrashLoopBackOff` and `resource/OOMKilled`) and one RemediationAction linked to the less specific one. It now raises one `resource/OOMKilled` incident that lists the crash-loop signals as contributing, and the RemediationAction's `incidentRef` names it. A crash loop with another cause is still its own incident. An existing open `CrashLoopBackOff` incident for an OOM-ing pod is resolved by the normal grace period once the signal is no longer reported under that name.

> **The model is asked once per changed situation, not once per cycle (harness P1 B4, task 1.7; KPI Q3, finding H-3).** An AI diagnosis or plan is cached by the group's signal fingerprint (category, severity, persona, and each signal's type, severity and workload; never message text, values or times) and reused until the signals change or `--llm-cache-ttl` (Helm `llm.cacheTTL`, default `30m`) runs out. A failed or unusable reply suppresses a retry for 5 minutes. `--llm-cache-ttl=0` restores a call every health-check cycle. Cluster-scoped groups (nodes, control plane) are no longer diagnosed at all, because nothing records them, and a group the planner would never act on (an `unattributed` incident) is diagnosed by the rules alone.
>
> **AI diagnosis replies are now structured and validated (task 1.6).** The model must return `{summary, rootCause, recommendedAction, confidence}`; anything else (prose, an unknown action, a confidence outside 0 to 1, extra fields, a key in the wrong case or repeated, control characters such as ANSI or OSC escapes in `summary` or `rootCause`) is discarded, counted in `dorgu_llm_invalid_output_total`, and the rule-based diagnosis stands. The incident's summary is the model's `summary`. The model's `recommendedAction` and `confidence` are advisory and are only logged: the rules own `SuggestedAction` and the deduplication key. Gemini is asked for a JSON reply and validated the same way.
>
> **A RemediationAction nobody approves now expires.** A `Pending` proposal older than 24 hours becomes `Expired`: terminal, nothing applied, no rejection or failure cooldown, and Dorgu may propose again if the problem persists. Tune it with `--remediation-pending-ttl` / the Helm value `remediation.pendingTTL` (`0` disables the TTL). A proposal's own `spec.approval.deadline` can shorten the window but never extend it. An action approved after its deadline is refused (`Expired`), not applied.
>
> **`RemediationAction` gains `status.gate`; apply the CRDs.** Helm does not upgrade CRDs, so run `kubectl apply -f charts/dorgu-operator/crds/dorgu.io_remediationactions.yaml` (or reinstall) before the new operator starts proposing. Nothing reads the field yet, and older operators ignore it. The spec fields it overlaps (`spec.workloadRef`, `spec.steps[].safety`, `spec.action.prePatchState`) are still written for one release; where they disagree, trust `status.gate`.
>
> **A persona the operator cannot clear is now refused when the rate limit cannot be read.** If the ClusterPersona list fails (lost RBAC, missing CRD), proposals are refused until it recovers, where before the limit silently reverted to the default of 5/h.
>
> **With the operator's own namespace unknown (`POD_NAMESPACE` unset), the gate now refuses every proposal, rule-based ones included, and AI diagnosis and AI planning are off** (the ClusterPersona carries an `OperatorNamespaceKnown=False` condition). The Helm chart always sets it; set it yourself when running the operator outside a cluster.
>
> **`ClusterPersona.spec.policies.selfHealing.excludeNamespaces` items are now validated by the CRD as DNS-1123 labels (at most 63 characters).** Apply the CRDs. An existing object with an entry such as `Shop` or `*` is rejected on its next update; fix the entry (it never matched anything).

> **Approval now goes through the gate again, and applies a ticket (harness P1 B5). Migration notes.**
>
> - **New phase `Ticketed`.** A human's approval no longer applies anything by itself: the controller re-runs the gate on live state (`ApprovalRecheck`) and either writes `status.applyTicket` (workload UID and resourceVersion, container, the merged persona patch, every verdict, `expiresAt`) and moves the action to `Ticketed`, or ends it as `Failed` with the `Applied=False` reason `GateRefusedAtApproval` and the refusing guardrail as a `GateRefused` condition reason (`BlastRadius`, `WorkloadGone`, `NoProposalRecord`, `SpecChanged`, `SelfHealingMode`, `Concurrent`, ...). A refusal applies nothing and starts no cooldown. The operator applies the ticket in the same reconcile, so `Ticketed` is normally visible only as a condition. Any client that watches `status.phase` for `Approved` to `Applying` should accept `Ticketed` in between. **Apply the CRDs** (new phase, new status field).
> - **`spec.action` is a notification only, with no patch (review fix F7).** `spec.steps[]` is the only plan; the rule engine writes its change as one persona-update step, and the operator now writes `spec.action` as `{type: notification}` with no `patch` and no `prePatchState`. The executor applies `status.applyTicket`, never `spec.action`, and an edit to the spec after the operator proposed the action refuses the approval. Read steps (or `status.gate`), not the action. **This does not stop an older CLI.** The released CLI (v0.13.0 and earlier) reads `spec.steps[]` first, finds the persona-update step and its patch, and patches the Deployment itself without asking for a ticket, whatever the operator does. **Upgrade the CLI to v0.14.0 together with or before the operator; an older CLI against this operator bypasses the ticket.** A v0.14.0 CLI against an operator from before tickets finds no ticket and refuses to patch, so the two still have to move as a pair. The operator cannot close this itself: it has no write verbs on Deployments, and closing it from the cluster side is P2 task 2.5 (admission policy `dorgu-action-integrity`).
> - **Only an action the operator proposed can be approved.** An approval needs the operator-written record of the proposal (`status.gate` from a cleared Proposal run, and the `Proposed` condition at the spec generation it cleared), and a workload UID in it. A RemediationAction created by hand, with `kubectl`, by an agent or by an older operator, is refused at approval (`NoProposalRecord`), and so is a proposal made against a persona with no resolvable Deployment (`WorkloadUnbound`): such a plan stays advice. Actions already `Applying` or `Verifying` when the operator upgrades have no ticket: they complete normally, but a rollback of one is refused (`Failed`, message says the change is STILL APPLIED).
> - **The CLI must be upgraded with the operator, and first.** A `dorgu` older than v0.14.0 reads `spec.steps[]`, not the ticket, so it patches the workload with no ticket and none of the checks above apply to that patch. Use the matching CLI (v0.14.0 or newer) before or at the same time as this operator. Until every machine that runs `dorgu remediation approve` is on v0.14.0, treat approval through an older CLI as the pre-ticket behaviour.
> - **A ticket is re-checked when it is applied (review fix F1, F3).** `Executor.Apply` runs `gate.Run(ApprovalRecheck)` again on live state and applies a ticket only if the gate would issue exactly that ticket (same patch, container and workload), with the approval history on record: `status.approvedAt`, the `Proposed` condition at the current spec generation, and `status.gate` as the approval re-check that cleared. A ticket also needs an `issuedAt` and a lifetime of at most 10 minutes. Anything else is refused as `Failed` with `Applied=False/PreconditionRejected` (no cooldown) and the guardrail as an enum on the `GateRefused` condition (`NotApproved`, `NoProposalRecord`, `TicketMismatch`, `ApplyTicket`, or whatever the re-run refused on: `SelfHealingMode`, `DenyList`, `NothingLeft`, ...). So a policy change after approval (observe mode, a protected namespace, a rate limit) refuses at apply. **Known P1 gap:** a client with `remediationactions/status` can still write a whole forged history together with a ticket; the re-derived patch limits what it can make the operator apply to what the spec's own plan produces, and the operator never writes workloads, but the CLI trusts a ticket it finds in status. Closing it is P2 task 2.5 (admission policy `dorgu-action-integrity`: the ticket and the phases after approval writable only by the operator ServiceAccount). The CLI carries stopgap checks until then.
> - **New CRD fields (apply the CRDs).** `status.applyTicket.issuedAt` (operator-set; the CLI accepts only a ticket issued at or after its own approval write), `status.applyTicket.observedGeneration` (the Deployment's `metadata.generation`, which the CLI compares instead of resourceVersion, so a status or scale write does not invalidate a good ticket), and the IncidentMemory resolution outcome `self-resolved`.
> - **A recovery with nothing patched is `self-resolved`, not `resolved` (review fix F10, N1).** If verification passes but the CLI never patched the Deployment (`--no-heal`, a declined prompt, a patch that changed nothing), the incident outcome is `self-resolved` and `HealCredited=False/NothingPatched` says so on the RemediationAction. `HealCredited=True` needs all of: the CLI recorded `WorkloadPatched`, the Deployment's generation moved past the ticket's, and the live container's resources equal the ticket's values (compared as quantities). A workload that changed but does not hold the ticket's values is `self-resolved` with `HealCredited=False/ResourcesNotTicket`. Count `resolved` for Dorgu heals and `self-resolved` separately.
> - **"Someone else changed the workload" is judged by what a write owns, not by who it says it is (re-review N1, N2).** A field manager name is chosen by the client, so `kube-controller-manager` and `dorgu` are no longer exempt by name. An entry written after the ticket is exempt only when its `managedFields` entry owns nothing but: for `kube-controller-manager`, the `deployment.kubernetes.io/revision` annotation (the only main-resource field the Deployment controller writes; its other writes are the `status` subresource and ReplicaSet objects); for `dorgu`, the container resource values the ticket patched. An entry with no readable fields is not exempt. Separately, a Deployment whose `metadata.generation` is past the ticket's `observedGeneration` plus one (the CLI's patch, recorded as `WorkloadPatched` or visible as a `dorgu` entry on the ticket's fields) is diverged, because a field deletion moves the generation and leaves no stamp. Both fail toward diverged: a heal over a diverged workload is `partial` with `WorkloadDiverged=True` and is not credited. **Known cost:** anything that changes the spec during the verification window, an HPA scaling the Deployment included, now reads as divergence and the heal is `partial`.
> - **A rollback never overwrites a later edit (review fix F4).** It restores a persona field only if it still holds what Dorgu wrote. A field someone changed after the heal is left alone, the incident outcome is `partial`, and the `PersonaEditedSinceHeal` condition names the field (`HumanEdited`; `NoBaseline` for a field the gate recorded no prior value for).
> - **The action class must match the rules (V2, from the #57 review).** A plan that contains a persona-update is refused (`ActionClass`) unless the rules' recommended action for the diagnosis is `resource-adjustment`. A model can no longer turn an image-pull diagnosis into a memory change.
> - **Observe mode at approval means refuse.** An approval that arrives after `selfHealing.mode` became `observe` is refused (`SelfHealingMode`).
> - **Rate limit, concurrency and dedup now read the API server, not the informer cache** (R11), and proposals for one persona are serialised, so two racing proposals cannot both be created. The operator makes more uncached `List` calls on RemediationActions per proposal.
> - **A `RolledBack` remediation now holds the persona quiet for the 30-minute failed-remediation cooldown (L4)**, like `Failed`.
>
> **Every gate refusal is now persisted three ways (harness P1 B6, task 1.10; KPI I3).** A refusal at proposal, at approval and at apply each get (1) a status condition with a reason enum, (2) a Kubernetes Event named `Dorgu<Stage>Refused` (`DorguGroundRefused`, `DorguModePolicyRefused`, `DorguGuardrailsRefused`, `DorguTicketRefused`, ...) and (3) a count in `dorgu_gate_decisions_total{phase,stage,result,reason}`. A refusal at proposal creates no RemediationAction, so it is recorded on the **IncidentMemory**: a `ProposalRefused` status condition (`True`, reason `<Stage>_<Reason>` such as `ModePolicy_SelfHealingMode`; `False/ProposalMade` once a later proposal succeeds) and a Warning Event. The same refusal on every 60 s cycle is written and emitted once. Refusals at approval and apply keep the `GateRefused` condition (reason = the guardrail, CamelCase) and now also emit the Event; `status.gate` names the refusing stage for approval refusals, and apply refusals are stage `Ticket`. No message text is parsed anywhere: the Unknown-verification retry counter that was read back from the `Verified` condition's message with `Sscanf` is now the condition's reason (`VerificationUnknownRetry1`, `VerificationUnknownRetry2`). **No CRD change; RBAC is unchanged** (the operator already creates Events). Reasons refined so a refusal says what it was: an expired ticket is `TicketExpired` (it shared `ApplyTicket` with "no ticket"), an unreadable self-healing mode is `PolicyUnreadable` and an unrecognised one `UnknownMode` (both used to be `SelfHealingMode`, which now means observe mode only), an apply of an action that is not `Ticketed` is `NotTicketed`, a cluster that could not be read to check the ticket is `ClusterUnreadable`, and a plan the clamps left nothing to ticket is `NoPlan` with a refusing verdict on `status.gate`. Dashboards or alerts keyed on `GateRefused` reason `SelfHealingMode` or `ApplyTicket` should add the new values.
>
> **Review round on #59 and #64 (what changed after the independent review).** (1) **An outstanding proposal is not a refusal.** The gate still holds the second proposal back (nothing proceeds), but `DedupCooldown/active-remediation` is now a *deferral*: counted as `dorgu_gate_decisions_total{result="deferred"}` and `dorgu_proposals_total{result="deferred"}`, never persisted as `ProposalRefused`, no Warning Event, and kept out of the refusal mix. A rejection cooldown stays a refusal. **`Guardrails/concurrent` is split by whose fix is in flight (second review round):** at proposal, an in-flight RemediationAction (Approved, Ticketed, Applying or Verifying) that answers the SAME incident, or changes the same field of the same persona, is the proposal already made and being worked, so it is the same deferral (`DedupCooldown/active-remediation`, `result="deferred"`); only another incident's fix on a different field, which holds the persona, stays `Guardrails/concurrent` and a refusal (at approval it also stays a refusal). A standing `ProposalRefused` is cleared (`False`, `ProposalMade`) when a proposal or deferral answers it and (`False`, `IncidentResolved`) when the incident is resolved, by a Dorgu fix or on its own, so it cannot stay `True` after a heal. (Third review round: the deferral check now looks at every sibling before it refuses, so an incident with a Pending proposal is deferred while another incident's fix on another field is in flight, in any listing order; the hourly rate limit no longer counts the incident's own *active* proposal, so `maxRemediationsPerHour: 1` does not "refuse" an incident for the proposal it already has, while a finished proposal of the same incident still counts and the approval phase is unchanged; and a deferral clears a standing refusal as `False/ProposalDeferred` ("an earlier proposal for this incident is outstanding or cooling down"), keeping `ProposalMade` for a real proposal.) (2) `dorgu_stage_duration_seconds{stage="detect_to_proposal"}` is observed once per incident, for its first RemediationAction; a later action for the same incident (after a failure or rejection) adds no sample. (3) A cleared approval with nothing left to ticket is counted once, as a refusal (`no-plan`), not first as a pass. (4) `dorgu_verifications_total`, `dorgu_heal_credit_total`, `dorgu_rollbacks_total` and `applied_to_verified` are counted after the status write succeeds, so a conflict that requeues the reconcile does not count them twice. (5) Event messages are truncated on a rune boundary, and the proposal refusal on the incident is written with the same retry as the rest of the incident store (it also survives a cache that has not seen the incident yet). (6) The refusal-site audit test now also covers variable-guardrail sites (declared, with every value they can take), keyed `TicketProblem` literals, and refusal verdicts written around `refuse()`; the pre-registration tests read the registry without creating series, and `internal/metrics/startup` checks a clean registry in a binary of its own. **Known and accepted:** an action that is mid-verification when the operator upgrades carries the old `VerificationUnknown` reason, so its retry count restarts at 0 and it gets at most two more retries (bounded, terminates). `dorgu_incidents_resolved_total` can miss a resolution whose incident write failed (the failure is logged and the RemediationAction itself shows the outcome); it is not retried.

> **Probe failures and recurrences are detected (harness P1 B9, dogfood D0.8 findings 1 to 3). Behaviour changes.**
>
> - **New health signals `ReadinessNotReady`, `LivenessRestarts` and `RestartLoop`, so incidents appear for faults that raised nothing before.** A running container that stays not Ready for `--readiness-threshold` (default `2m`, Helm `healthCheck.readinessThreshold`) raises a `health` incident, counted from the container start plus the readiness probe's `initialDelaySeconds`, with the kubelet's `Unhealthy` readiness events as supporting evidence. A container restarted `--liveness-restart-count` times (default `2`) within `--liveness-restart-window` (default `10m`, Helm `healthCheck.livenessRestarts.count` and `.window`) raises one without waiting for CrashLoopBackOff, and the kubelet's own "Container X failed liveness probe, will be restarted" `Killing` events decide which kind: with such an event in the window it is `LivenessRestarts` whatever the exit code (a liveness kill is a SIGTERM first, so an application that handles it exits 0), and with none, an `Error` or SIGKILL exit is a `RestartLoop` of unknown cause, because an application that crashes quickly looks exactly like it. The restart delta is observed across cycles: after an operator restart a container is only seeded on first sight (its lifetime restart count proves nothing about the window), though at least `--liveness-restart-count` kill events in the window are enough on their own. All three are `warning`, category `health`, action `investigate` (advice), and go through the same diagnosis, structured AI path and gate as every other incident. **Expect new incidents after upgrading** on workloads that were quietly unhealthy. An app that legitimately takes longer than the threshold to become Ready should have a `startupProbe` (a container whose startup probe has not passed is never reported) or a longer threshold. One container is one finding at a time: CrashLoopBackOff or a live OOMKilled on the container wins and the new signals are not raised for it, and `LivenessRestarts` and `RestartLoop` win over `ReadinessNotReady`. **`--liveness-restart-window` must be at least twice `--health-check-interval`:** the restart history is one observation per cycle, and the operator refuses to start with a clear error otherwise, rather than run with a signal that could never fire.
> - **A fault that comes back after its incident resolved is a new IncidentMemory, never folded into the Resolved one.** Before, the stable incident name collided with the Resolved record, which stayed `Resolved` while its `occurrenceCount` rose, got no proposal and was hidden from `dorgu incidents list`. The recurrence now has its own `firstSeen` (so time to detect and detect-to-proposal are measured per recurrence), the name `<first-name>-r<N>`, the annotations `dorgu.io/recurrence-of` (the incident it recurs) and `dorgu.io/recurrence-count` (earlier incidents of this fault), a `Recurring=True` condition with reason `RecurrenceOfResolvedIncident`, and the counter `dorgu_incident_recurrences_total{class,scope}` (also counted in `dorgu_incidents_total`). The Resolved incident is left exactly as it was. No CRD change. The gate treats all records of one fault as one lineage: an active proposal for an earlier incident of the fault still defers a new one, a rejection still holds for its cooldown, and the persona-wide failed-cooldown is unchanged. A finished fix that did not hold, an expired proposal and a cooldown that has run out all allow a new proposal. The hourly rate limit uses the same lineage, so an outstanding proposal of the fault is a deferral and not a `Guardrails/rate-limit` refusal.
> - **A container that was OOM-killed, and has been Running and Ready since for 2 minutes (or twice `--health-check-interval`, if longer), is no longer an OOMKilled signal.** The pod keeps `lastState.terminated` until it is replaced, so the signal, the incident and a model call used to come back every cycle. A kill within that window is still detected, and a container that is not Ready is never treated as stale. The open incident then resolves through the normal grace period and stability check.
> - **A fault that changes shape is one incident, not one per shape.** A container that goes not Ready, then is restarted by the kubelet, then enters CrashLoopBackOff, then is OOM-killed used to open an incident for each. The identity of a fault is the application, the container and the family (`ReadinessNotReady` < `RestartLoop` < `LivenessRestarts` < `CrashLoopBackOff` < `OOMKilled`); the pod is not part of it, so a pod replaced by a rollout still merges. A worse signal **escalates** the open incident (its signal, category and severity become the new ones); a milder signal while the worse one is still being seen for the container is **folded** in; a milder signal once the worse one has cleared **de-escalates** it, so signal, category and severity follow the current state down. It keeps its name, `firstSeen` and count, the path is kept in `dorgu.io/escalated-from` (the last 16 entries), `dorgu.io/containers` names the containers it is about, and `dorgu.io/escalated-at` says when it last escalated. Different containers, sidecars included, are different incidents, and so are two pods of one application failing in different ways at the same time. The same signal on two containers is still one incident, as it always was (the rules aggregate one signal's sightings), and it names both. Diagnoses of one pod are no longer collapsed when their primary signals differ. An existing `CrashLoopBackOff` incident for a container that is then OOM-killed is now escalated to `OOMKilled` (category `resource`) instead of leaving two.
> - **An escalation supersedes the proposal for the milder shape.** A `Pending` RemediationAction of an incident that escalates (matched by lineage, so one left by an earlier generation of the same fault counts) becomes `Expired` with the new condition reason **`Superseded`** (the other reason is `ApprovalTimedOut`), plus a `DorguSuperseded` Event and a `Pending` to `Expired` transition, so the worse shape is proposed in the same cycle. Only a proposal for a **strictly milder** shape is superseded: one that answers the shape the incident now has, or a worse one, stays, so a fault that flaps between shapes keeps its standing proposal instead of expiring and re-minting one each time. A proposal made before proposals recorded what they answered is superseded only if the incident escalated after it was created (`dorgu.io/escalated-at`); with no such stamp, or one that is not after it, it is kept and the gate defers behind it. It is not a rejection and starts no cooldown. `Approved`, `Ticketed`, `Applying` and `Verifying` proposals are never superseded: the worse shape waits for them. A superseded proposal cannot be approved: the CLI only approves `Pending` ones, and if an approval is forced onto the status the operator puts it back to `Expired` and issues no ticket. The CLI shows a superseded proposal as `Expired` (the reason is in `dorgu remediation describe`'s conditions); clients that read the `Expired` condition reason should accept `Superseded`.
> - **A rejection is a no to the shape it was made for.** Proposals now carry `dorgu.io/answers-signal`. A rejection of the milder plan no longer holds the proposal for a strictly worse shape of the same fault, while a rejection of the worse shape still holds for the milder one; a rejection that does not say what it answered (made before this release, or by hand) is released by the incident's `dorgu.io/escalated-at`. The cooldown still follows the lineage across recurrences.
> - **A flapping fault is capped, and old Resolved incidents are pruned.** After `--incident-recurrence-cap` recurrences of one fault (counted per application, container and family, whatever shape each was in, not per signal) within `--incident-recurrence-window` (defaults `3` in `24h`; Helm `healthCheck.recurrence.cap` and `.window`; `0` disables the cap) the next recurrence reopens the latest incident instead of creating another: it is open again (never a silent fold into a Resolved record), it takes the shape the fault has now, its sighting is counted and `lastSeen` refreshed, the record of the resolution it replaces is kept in `dorgu.io/last-resolution`, it gets the annotation `dorgu.io/recurrences-folded`, the `Flapping` condition, and one Warning Event (`DorguIncidentFlapping`) the first time. The counter is `dorgu_incident_recurrences_capped_total{class,scope}`. Resolved incidents whose last sighting is older than `--resolved-incident-retention` (default `720h`; Helm `healthCheck.resolvedRetention`; `0` keeps them forever) are deleted, except the newest Resolved incident of every fault (so a recurrence still numbers on from it and links to it) and any incident a non-terminal RemediationAction names; counted in `dorgu_incident_prune_total{result}`. The candidates are chosen from the cache but confirmed against the API server before anything is deleted: the incident is read live, must still be the same object, Resolved and past the retention, no live non-terminal RemediationAction may name it, and the delete carries the live `resourceVersion` as a precondition. `--resolved-incident-retention` shorter than `--incident-recurrence-window` is refused at startup, since pruning would delete the incidents the cap counts. What pruning loses is the older generations' own records (root cause text and timings); the newest record keeps its `dorgu.io/recurrence-count`, and its `dorgu.io/recurrence-of` may then name a deleted incident. **The operator's ClusterRole gains `delete` on `incidentmemories.dorgu.io` and nothing else** (`kubectl auth can-i delete deployments` is still `no`): upgrade the chart, or pruning fails with a Forbidden error per incident and nothing else changes.

### Fixed

- **One bad image is one incident and one proposal (EKS QA F-1).** A pod whose image cannot be pulled stays `Pending`, so it also crossed the long-pending threshold five minutes in and opened a second incident (`PodPendingLong`) with its own proposal. The pod collector no longer raises `PodPendingLong` for a pod with a container (init containers included) waiting on `ImagePullBackOff`, `ErrImagePull` or `InvalidImageName` (the last now also raises the image-error signal). If the two still meet, the `PodPendingLong` diagnosis is folded into the image-error incident; and when `PodPendingLong` came first and the image error follows, the Pending proposal made for the pending pod is superseded (`Expired`, reason `Superseded`) before the image error is proposed for. A pod that is Pending for any other reason is unchanged.
- **A container that exits right after it starts is detected within about a minute, not five (EKS QA F-4).** Such a container is `Running` for a few seconds of each back-off cycle and sits in `Terminated` (reason `Error`) the rest of the time, so the restart-loop signal, which needed a Running container, never fired and the incident waited for CrashLoopBackOff (about the fifth restart). `RestartLoop` and `LivenessRestarts` now also read a container between runs, from its current termination. For a pod younger than the restart window (`--liveness-restart-window`, 10 minutes), every restart it has had happened inside the window, so its restart count is the delta at the first sighting instead of waiting for two restarts to be observed (the kubelet's back-off doubles the gap between restarts, which made that about two minutes). Measured on EKS: 117 s before this, about 60 s after. An older pod's lifetime count still only seeds the history. CrashLoopBackOff still owns the container, and suppresses the probe signals, only in a cycle in which it fired for that container; the incident then escalates in place (the B9 family).
- **A proposal that predates the gate expires instead of failing (EKS QA F-3)** and **an advisory plan is proposed when the AI plan's persona change is refused (F-5)**: see the migration checklist.
- **The leader lease is released when the manager stops (EKS QA F-6).** `LeaderElectionReleaseOnCancel` is on, so a rolling update no longer leaves detection without a leader for the lease duration (about 30 s was measured after each `helm upgrade`). The process exits as soon as the manager returns; keep it that way.
- **A recurrence after Resolved no longer folds silently into the Resolved incident (harness P1 B9, D0.8 finding 2)** and **a stale `OOMKilled` terminated state is no longer a live signal (finding 3)**: see the upgrade notes. Regression tests for **F-13** now cover CrashLoopBackOff, OOM, readiness and liveness faults in deny-listed and excluded namespaces end to end (no incident, no proposal, no model call), with an ordinary-namespace control.
- **Expected races no longer log at ERROR or count as reconcile errors (harness P1 B7, findings F-10 and Z1 F-1).** An optimistic-lock conflict (`the object has been modified`) on an IncidentMemory, ApplicationPersona, ClusterPersona or ArgoCD-driven persona write now requeues a second later instead of returning an error (which controller-runtime logs at ERROR and counts in `controller_runtime_reconcile_errors_total`). A persona, incident or namespace deleted mid-cycle (a named object that is `NotFound`, or a terminating namespace) is logged at V(1) in the incident controller, the health cycle (it is no longer counted as a discarded diagnosis) and the event watcher. A `NotFound` that names no object, which means a resource type or CRD is missing, and every other error stay at ERROR. The RemediationController's own approval and ticket status writes follow the same rule (harness P1 B5, re-review N4): a conflict requeues after a second at V(1), and a failed approval re-check is returned once instead of being logged at ERROR and returned.
- **Pod detection honours the deny-list** and **one OOM raises one incident**: see the upgrade notes (F-13, F-9).

- **The AI plan cache now hits (review of #57, V1).** `planner.PlanFingerprint` hashed the whole `WorkloadRef`, including `ObservedAt`, which the gate stamps with its clock on every proposal, so no two cycles ever shared a key and a failing or refusing planner was asked again every cycle (10 planner calls in 10 cycles, where the bound is 3). The key now lists the stable fields only: kind, name, namespace, container, managedBy, and the observed image and resources. The cost test now runs the gate on a moving clock. The diagnosis fingerprint was audited for the same mistake and has none; a moving-clock test pins it.
- **Model text can no longer smuggle terminal escapes or a second value into an incident (review of #57, V3, V4).** A `summary` or `rootCause` containing a C0 or C1 control character other than newline and tab (ESC, BEL, CR, DEL, U+009B and so on, which carry ANSI CSI and OSC sequences) is rejected like any other invalid reply: rule-based fallback, counted in `dorgu_llm_invalid_output_total`. The reply is decoded strictly: keys are case-sensitive and a repeated key is an error (`encoding/json` would have accepted `{"summary":"a","SUMMARY":"b"}`). The cluster text in the diagnosis prompt (the rule summary and the signals) is fenced between `<<<SIGNALS` and `SIGNALS>>>` markers, one line per item, with control characters and the markers themselves removed.
- **A verifier or health cycle whose collectors failed no longer reads "could not look" as "saw nothing" (harness P1, task B2b).** `detection.Engine.CollectAll` logged a failing collector and carried on, so a verifier whose collectors all errored (lost RBAC, API timeouts) saw no signals and reported `Healthy`, and the remediation was marked `Completed` without ever being checked. `CollectAll` now returns the working collectors' signals together with a `*detection.CollectionError` naming every collector that failed. Verification with any failed collector is `Unknown` (never `Healthy`), which retries and then rolls back as before. The health cycle still records what the working collectors saw, but resolves no incident in a cycle where any collector failed: absence of a signal is only evidence when every collector ran.
- **Verification retries on `Unknown` now terminate, and a change that cannot be verified is rolled back (harness P1, task 1.8; adversarial OP-12).** The retry counter lives in the `Verified` condition's message, and `setCondition` left the message alone when status and reason were unchanged, so it stuck at `retry 1/2` and the action stayed `Verifying` forever with the change applied. The counter now advances, and after two retries the action rolls back (`RolledBack`, reason `VerificationUnknown`). If the rollback itself cannot run (disabled, no `prePatchState`), the action is `Failed` and its message says the change is STILL APPLIED to the ApplicationPersona.
- **The verifier no longer reports `Healthy` for a persona it could not identify (adversarial OP-13).** `personaRef.namespace` is optional; the verifier compared it verbatim, so an empty namespace matched none of the persona's signals and a still-failing application verified `Healthy`. It now falls back to the action's namespace, then the incident's; with no persona name or no namespace at all it reports `Unknown` with an error.
- **A rollback that did not reach the workload is recorded as `partial`, not `rollback`.** When the persona was restored but the live Deployment still carries the change (the operator has no write verbs on Deployments), the IncidentMemory resolution outcome is `partial` and the `RolledBack` condition says which half was restored; `WorkloadDiverged` carries the command that finishes the job. A failed rollback says the change is still applied.

### Known limits (review of #57, V5)

- **A cached AI summary can be up to `--llm-cache-ttl` (30 minutes by default) old.** While the signal fingerprint is unchanged, the incident shows the first answer the model gave, which can name a pod that has since been replaced or describe an older restart count. The prompt now tells the model to name the Deployment, not a pod, and not to quote counts; the authoritative occurrence count is `status.occurrenceCount` on the IncidentMemory, which the rules maintain, not the summary text. The cache holds at most 1024 entries, so a very noisy cluster can evict a quiet incident's answer early (it is then asked again). Concurrent first requests for one fingerprint are not collapsed. Set `llm.cacheTTL` lower for fresher text at a higher call count.

### Known gaps (harness P1 B9)

- **CPU throttling is not detected (deferred to P2).** A container throttled for 97% of CFS periods for three minutes raised nothing in the dogfood run (D0.8, finding 1). Detecting it needs a metrics source (cAdvisor or Prometheus `container_cpu_cfs_throttled_periods_total`); the operator reads neither today, and the existing CPU signals come from metrics-server usage, which does not see throttling.
- **A Pending proposal for a Resolved incident stays Pending.** When a fault resolves by itself and then recurs, the earlier proposal is still outstanding, so the gate defers a new one (one proposal per fault, not two). It expires after `--remediation-pending-ttl`. Superseding it at resolution is not done.
- **An exit 0 after a liveness kill is only detected with the kubelet's events.** If the events have aged out (they are kept about an hour) or cannot be read, a container that exits 0 on every restart is not reported; an `Error` or SIGKILL exit still is, as a `RestartLoop`. `--liveness-restart-window` longer than the event retention is therefore not useful.
- **Staleness of a terminated state trusts the node's clock against the operator's.** A node whose clock is behind by more than the grace (2 minutes, or twice the health-check interval) can make a fresh OOM kill of an app with no readiness probe look old, and it is then not reported. Skew in the other direction only keeps a signal alive longer. Skew on a managed cluster is normally milliseconds.
- **Restarts are dated when they are observed**, so one can read up to a cycle younger than it is, and the delta is a lower bound when the collector has not been running for the whole window.
- **`ProbeFailure` and `ContainerHighRestarts` still produce no diagnosis on their own** (they only add context to a CrashLoopBackOff). `ContainerHighRestarts` counts lifetime restarts and never goes stale.
- **The Resolved/open reading of an incident is `status.phase`.** The `dorgu.io/phase` label, which anyone who can edit an incident can set, is only an index for listing; nothing is deleted on its word.
- **A kill by a failing startup probe is not matched.** Only `failed liveness probe` events count as evidence, so an exit-0 startup-probe kill is missed, and an `Error` exit is reported as a `RestartLoop` whose rule says no event blames a probe.
- **`dorgu.io/answers-signal` (on RemediationActions) and `dorgu.io/escalated-at` (on incidents) are ordinary, user-writable annotations.** A user with update rights on RemediationActions or IncidentMemories can edit them and so release a rejection cooldown early. It only lets the operator create one more `Pending` proposal, which still needs a human, and it is the same tier as editing `spec.incidentRef` or lowering an incident's `spec.severity`, which already released it. Hardening is planned for P2 task 2.5: operator-written status that the shape and the escalation time are read from, with an admission policy making the rest immutable.
- **Closed on the CLI side in v0.14.0 (R2-3):** the CLI used to approve with a merge patch that carried no `resourceVersion`, so it could print "approved" for a proposal the operator then put back to `Expired` (nothing was applied and no ticket was issued). CLI v0.14.0 patches with a `resourceVersion` precondition, re-reads after a short settle and reports "approved" only if the approval stands; otherwise it names the phase (`Superseded`, `Expired`) and exits non-zero. Use CLI v0.14.0.
- **A reopened incident is re-counted as Resolved at every re-resolution** (`dorgu_incidents_resolved_total`), and its detect-to-proposal is measured from the original `firstSeen`.

### Known gaps (CP1 release, planned)

- **CPU throttling is not detected (P2).** See the B9 gap above: it needs a metrics source (cAdvisor or Prometheus) the operator does not read.
- **Status-RBAC ticket forgery (P2 task 2.5).** The apply ticket lives in `status.applyTicket` and the CLI trusts it. Anyone who can patch `remediationactions/status` (a CI service account, a cluster admin) can write a ticket, or an approval, by hand, and the CLI will apply it if the ticket matches the live Deployment's UID and generation. The operator's own gate cannot stop that, because the write bypasses it. Admission policy on status writes (`dorgu-action-integrity`, P2 task 2.5) makes the operator the only writer of the ticket. Until then, treat `patch` on `remediationactions/status` as the right to approve.
- **User-writable annotations (P2 task 2.5).** `dorgu.io/answers-signal` and `dorgu.io/escalated-at` can be edited by anyone with update rights on the object (see above). The same admission policy covers them.
- **Identity gaps ID-01 to ID-04 (CP2).** The adversarial suite catalogues four open scenarios and the operator group is at 16/20: ID-01 (any status writer can approve), ID-02 (no proposer-is-not-approver rule), ID-03 (`approvedBy` is free text), ID-04 (nothing restricts who creates RemediationActions). They need the CP2 identity work and are expected to stay open at this release.

### Changed

- **LLM calls are structured, bounded and counted (harness P1 B4, tasks 1.6 and 1.7; adversarial OP-11).** Diagnosis and the AI planner now share one provider interface, `llm.Client.Complete`, instead of two separate Anthropic implementations, so there is one place a request is sent and counted. The free-text reply used to be substring-matched for an action name and written into `SuggestedAction` and so into the deduplication key ("Do not restart the pod" selected `restart`); that code is gone. Simulated over 10 unchanged health cycles, the four-scenario set that cost 11, 20, 10 and 10 model calls (51 in all) now costs 2, 2, 0 and 0.
- **The diagnosis prompt states the incident's real history.** It carried no history at all (and before P0 a false "0 previous occurrences"); it now says "first sighting" or "seen N time(s) before this cycle", read from the incident's `occurrenceCount`.
- **The "cannot read the ClusterPersona" ERROR lines are rate-limited** (deny-list, rate limit and mode, one per site every 5 minutes, with a `suppressedSinceLastLog` count) instead of once per proposal attempt per cycle. The refusals themselves are unchanged (#51 follow-up).
- **Review fixes to the gate (independent adversarial review of #54, R1 to R12).** The gate measures the `Action` the executor applies as well as the steps (a benign step beside a 999Gi `Action.Patch` no longer passes). A workload that is deleted or ambiguous at approval, a persona that does not exist (at proposal too), an unreadable Deployment list, and a field with no baseline to measure against all refuse or clamp, each with its own reason (`workload-gone`, `workload-ambiguous`, `persona`, `no-baseline`). With several ClusterPersonas the most restrictive `mode` and the lowest `maxRemediationsPerHour` win, and an unreadable or unrecognized mode refuses. `excludeNamespaces` is compared trimmed and lowercased. A step `command` must be one plain `kubectl` invocation (no wrapper, absolute path, `&&`, pipe, substitution, quotes, or flag that names another cluster or identity), and a persona patch must be a JSON object without dotted keys (`step-command`, `patch-shape`). A Deployment with a controller ownerReference reads as owned; only Dorgu's own field managers (`dorgu`, `dorgu-operator`) and kubectl's client-side Update managers are benign, so a server-side `kubectl apply` pipeline reads as owned. `status.gate` is now the decision of the final seal run on the plan that was written, and a RemediationAction whose status cannot be written is deleted and reported as an error instead of `Proposed`.
- **Review findings M1, M2, M3, L1, L4 and the R11 cache race (B5).** `Run` treats ApprovalRecheck as Final whatever the caller says (M1). ### Upgrade notes

> **With AI on, incidents in a protected namespace are now recorded `provider=rule-based`, not `ai-enhanced`.** Their context is no longer sent to the model. Detection, diagnosis and the incident record are unchanged. No values or flags change, and no new RBAC is needed (the chart already grants `clusterpersonas` list).

### Security

- **Incidents in a protected namespace are no longer sent to a model, by the diagnosis call or the planner (EKS QA 2026-11-06, F-1).** The deny-list (`kube-system`, the operator's own namespace, `safety.excludedNamespaces` / `--safety-excluded-namespaces`, ClusterPersona `excludeNamespaces`) gated the remediation planner only, and only on the diagnosis' `PersonaRef` namespace. `AIProvider.Diagnose` still called `EnhanceDiagnosis` once per diagnosis per cycle with no check, so an incident in `dorgu-system` sent its summary, severity and signal strings such as `Pod/dorgu-system/<name>` to the provider every cycle and was recorded `provider=ai-enhanced`. The planner had a second gap: node-pressure and saturation diagnoses merge signals from pods in many namespaces under the first persona found, and the planner prompt carries every contributing signal's message, so a diagnosis with an allowed persona could still name a `dorgu-system` pod (for example one evicted by a node under pressure) and pass the check. Both paths now use one enumeration of the namespaces a diagnosis touches (`diagnosis.ProtectedNamespace`: its persona, its affected resources and the resource behind every contributing signal) and one predicate over it (`SafetyCheckerImpl.NamespaceProtected`, which is `NamespaceDenied` as a yes/no), so they cannot disagree. A diagnosis touching any protected namespace is withheld whole. The incident is still detected, diagnosed by the rules and recorded, now as `provider=rule-based`; where the planner is withheld, `Propose` falls through to the rule-based proposal, which never calls a model. The planner prompt also no longer lists the ClusterPersona `excludeNamespaces`: it used to send the names of the namespaces meant to be invisible to the model with every plan request. It also no longer follows an IncidentMemory's remediation reference out of the persona's namespace, since an incident is writable by anyone with access to its namespace and the referenced action's explanation goes into the prompt. The deny-list fails closed: a persona or namespaced resource with no namespace, a `nil` gate or checker, or a ClusterPersona list that cannot be read counts as protected. That last case used to be waved through as allowed; it now refuses in `NamespaceDenied`, which the proposer's pre-planning gate and `SafetyChecker.Check` (called only while proposing, not by the remediation controller, executor, rollback or verifier) both use, so in-flight RemediationActions are unaffected. The read failure is logged at error level (the raw API error stays in the log; the skip reason carries a fixed message), because while it lasts every AI call and proposal in an unprotected namespace is refused. An empty `PersonaRef.Namespace`, which `Propose` used to treat as `default`, is now refused at the gate (unreachable in production today, the correlator always sets it). Cluster-scoped `Node` and `ComponentStatus` signals carry no namespace by nature and are still enhanced. Adversarial scenarios OP-15 (diagnosis, with a positive control) and OP-16 (the mixed-namespace eviction against the planner) count the requests that actually reach the model API; `make adversarial` now reports N/20. Unchanged: behaviour in non-protected namespaces, the one-call-per-diagnosis-per-cycle cadence and the absence of a call metric (H-3, tracked separately), and the RBAC and flags.

### Upgrade notes

> **The deny-list now protects the namespace the operator runs in** (typically `dorgu-system`), where it used to protect only `dorgu-operator-system`. Workloads in that namespace are no longer eligible for proposals.
>
> This release also carries the unreleased fixes from #49 (CR5-01, CR5-02, CR5-03), listed under Fixed.

### Added

- **Adversarial bypass suite (`test/adversarial/`, `make adversarial`).** One envtest test per attack in `test/adversarial/SCENARIOS.md` (OP-01 to OP-14, ID-01 to ID-04), each asserting the safe outcome against the real controllers. Holes not yet closed are listed once in `openScenarios` with the checkpoint that must close them and skip as `OPEN`; a listed scenario that starts passing, or an unlisted one that stops passing, fails the suite. `make adversarial` ends with the KPI I1 line, `adversarial: blocked N/18`.

- **Harness metrics on the existing metrics endpoint.** `dorgu_incidents_total{class,scope}` counts incidents opened, by diagnosis category and attribution; `dorgu_proposals_total{source,action_type,result}` counts every proposal attempt with its result (`proposed`, `skipped`, `suppressed` by a recent rejection, `error`), so refusals that were only logged at V(1) are now measurable; `dorgu_remediation_transitions_total{from,to}` counts every RemediationAction phase change the operator writes. They register on controller-runtime's registry, so no new port or ServiceMonitor is needed.

### Security

- **The Gemini API key is sent in the `x-goog-api-key` header, never in the URL.** It used to travel as `?key=...` in the request URL, which ends up in proxy logs and in Go's `*url.Error` text; a network failure therefore wrote the key into the operator's error log. Error messages from both LLM clients also redact the key if a provider's error body echoes it back.

### Removed

- **The Deployment validating webhook (`internal/webhook`), and with it the `--enable-webhook`, `--webhook-mode`, `--webhook-cert-path`, `--webhook-cert-name` and `--webhook-cert-key` flags and the chart's `webhook.*` values, Service and `ValidatingWebhookConfiguration`.** It never worked: `cmd/main.go` built the validator without a decoder, and the `InjectDecoder` hook that would have set one was removed from controller-runtime long before v0.23, so every admission request dereferenced a nil decoder, panicked, was recovered as a 500 and admitted by `failurePolicy: Ignore`. No warning or denial was ever produced. Admission for Dorgu's own CRDs arrives as ValidatingAdmissionPolicies in a later release. **Breaking:** passing a removed flag stops the binary from starting, and `helm install`/`upgrade` with `webhook.enabled=true` now fails with a message saying the webhook was removed, rather than silently dropping the value.

- **The legacy ApplicationPersona OOM proposer (OP-10).** With `--enable-health-check=false` (or `healthCheck.enabled=false`), the ApplicationPersona reconciler still opened OOMKilled incidents and wrote RemediationActions itself, with no safety check, ownership check or mode check, and with a patch the executor could not even apply (it lacked the `spec` wrapper). The documented promise that turning the health check off means Dorgu never opens an incident or proposes a fix is now true. The ApplicationPersona reconciler records health only; its unused `WebSocket` field is gone with it.

- **Dead code with no caller (P0 0.12).** `IsArgoCDInstalled` (the watcher uses `ArgoCDCRDExists`); the never-broadcast WebSocket functions `BroadcastPersonaEvent` and `BroadcastClusterEvent`, their `PersonaEvent`, `ClusterEvent` and unused `ValidationEvent` payloads, and the `events` and `deployments` topics nothing publishes to; the four `health-update` fields that were always zero or empty (`nodeCount`, `healthyNodes`, `cpuUtilization`, `memUtilization`); `EventStore.Query` and `Count` with the in-memory read cache behind them, since nothing reads events back and the DorguEvent objects are the record; and the LLM request's `PreviousOccurrences`/`PreviousResolutions` and response's `ConfidenceAdjustment`, which nothing populated. The first two meant every diagnosis prompt told the model "Incident history: 0 previous occurrences, previous resolutions: none" regardless of the incident's real history; that false line is gone from the prompt.

### Changed

- **The deny-list protects the namespace Dorgu actually runs in (OP-03).** It hardcoded `dorgu-operator-system`, the kustomize default, while the chart installs into the release namespace, typically `dorgu-system`, which was therefore not protected at all. The operator now reads its namespace from `POD_NAMESPACE` (set from the downward API by both the chart and `config/manager`), falling back to the mounted service account namespace. `kube-system` stays protected. New chart value `safety.excludedNamespaces` and flag `--safety-excluded-namespaces` add more; ClusterPersona `excludeNamespaces` still applies.

- **`--enable-health-check` now defaults to `true` in the binary,** matching the chart, which has defaulted `healthCheck.enabled` to `true` since 0.8.0. Running the binary without flags no longer silently disables detection. The README configuration table, which still said `false`, is corrected.

### Fixed

- **The chart injects the API key env var that matches `llm.provider`.** It always injected `ANTHROPIC_API_KEY`, so `llm.provider=gemini` started an operator that looked for `GEMINI_API_KEY`, found nothing and quietly ran without AI. `llm.existingSecretKey` now defaults to the provider's env var name (`ANTHROPIC_API_KEY` or `GEMINI_API_KEY`); an explicitly set key name still wins, so existing Claude installs render exactly as before. An unsupported `llm.provider` now fails the install instead of rendering an operator that ignores it. AI remediation planning remains Claude-only; with Gemini, diagnosis is AI-enhanced and plans stay rule-based.

- **A flag value named after a read-only verb can no longer hide a write (kubectl verb-scan bypass).** Ownership shaping decided whether a suggested command writes by scanning for the first token that matched any known verb, so in `kubectl -n logs delete deployment/foo` the namespace `logs` was taken for the verb and the delete stayed in a plan for a Helm- or Argo-owned workload. The verb is now found positionally with a table of kubectl global flags (a value-taking flag consumes its value; an unrecognised flag makes the command a write rather than a guess), ported with its table tests from the dashboard so the operator, CLI and dashboard classify identically. Two more holes of the same shape are closed with it: `kubectl auth` is no longer read-only as a whole (`auth reconcile` writes RBAC; only `auth can-i` and `auth whoami` read), and the subcommand of `rollout` and `auth` must be the very next token, so `kubectl rollout -n status restart deploy/x` is a write.

- **A value a guardrail refused can no longer appear on any surface a client renders (CR5-01).** Clean-room run #5 approved a plan whose blast-radius verdicts had just refused `512Mi` and `256Mi` against a live `8Mi` baseline, and three lines below the refusal, on the final confirmation screen before `[y/N]`, Dorgu printed `kubectl set resources deployment/drifted --containers=drifted --limits=memory=512Mi --requests=memory=256Mi -n drift` as a copy-paste command. The workload was unmanaged, so the paste actually lands, and the plan's own rationale called the write "safe". One paste defeats the product's central safety claim, performed by a user doing exactly what the plan told them to do.

  This is the second instance of the same defect. 0.11.0 fixed it for owner instructions by moving `applyOwnershipShaping` below the guardrails; `workload-apply` steps on unmanaged workloads were the one path that fix did not cover, and they are the one path where the command is runnable. Two instances in two places is a pattern, so the fix is not a third local patch. `scrubRefusedValues` is a single chokepoint immediately before the `Create`: it reads the structured verdicts already recorded on the steps and removes those values from patches, commands, descriptions, rationale, the plan summary and the explanation alike. Refusals are collected across the whole action rather than per step, because CR5-01 was a value refused on step 1 being re-offered by step 2. Quantities are compared numerically as well as literally, so `268435456` is recognised as the `256Mi` that was refused, while `1256Mi` is not.

  A command that carries a refused value is dropped rather than rewritten, and the step says why. Rebuilding an arbitrary `kubectl` invocation from a post-guardrail patch means parsing a grammar Dorgu does not own, and a half-corrected command that still looks runnable is worse than no command at all. Two things are deliberately left alone: `spec.steps[].safety[].message`, because a refusal that cannot name what it refused explains nothing, and `prePatchState`, because it records what the persona holds now. In the clean-room case it genuinely held `512Mi`, so pruning it would break rollback and turn an accurate `512Mi -> 16Mi` diff into a lie.

- **No surface asserts a guardrail ruled unless one recorded a verdict (CR5-03).** On two plans that asked for exactly 2x, nothing was clamped, `spec.steps[].safety` was `null` on every step and no `GUARDRAIL` column appeared. And yet the sentence "Clamped by the 2x blast-radius guardrail: … could not be raised further in one step" appeared three times regardless, in `explanation`, in `planSummary` and in a step's `rationale`, two paragraphs from the model's own statement that it had chosen to double. The two claims contradict each other and nothing tells the reader which one was computed. Worse, `explanation` is copied verbatim into `IncidentMemory.spec.resolution.action`, so the fabricated verdict outlived the incident it was invented for.

  `scrubFabricatedGuardrailClaims` runs alongside the CR5-01 chokepoint and removes guardrail assertions from the plan's prose whenever no step carries a `safety` entry. It is keyed on the recorded verdict rather than on who wrote the sentence, because there are two authors and neither can be trusted to police itself: prompt rule G7 already forbids the model from commenting on caps and does not prevent it, and the sentence the clean room actually read was Dorgu's own at-the-cap disclosure calling *sitting at* a ceiling *being clamped by* one. A prompt is a request, not an enforcement point. Both paths are covered, rule-based and AI.

  **Consequence worth knowing about:** the F-11 disclosure now only appears when a guardrail genuinely refused a value. A plan that chose 2x for itself is still reported as less certain (confidence damping is untouched, `0.86` becomes `0.73`), but it no longer carries prose about the cap, because the guardrail did not constrain it. Restoring an honest version of that disclosure means recording "at cap" as structured data in `spec.steps[].safety`, which is a CRD enum change and a rendering change in the CLI, so it is deliberately not in this change.

- **A rollback that could not reach the workload now says so (CR5-02).** Verification found the health degraded, the operator restored the `ApplicationPersona`, and wrote phase `RolledBack` with "Remediation rolled back due to degraded health". The live Deployment kept the `16Mi` the heal had put there. There was no condition, no event, no log line and no CLI hint. "RolledBack" is a strong word: a reader takes it to mean the workload returned to its prior state and does not then go and diff the Deployment. Meanwhile the persona and the cluster now disagree in a new direction, and the next proposal re-anchors its blast radius on the still-changed live value.

  The operator is not given write access to Deployments to fix this. It holds `get`, `list` and `watch` on `apps/deployments` and nothing else, that restriction is the product's central promise, and `/security-and-permissions` documents it. What it can do is read. After a successful persona rollback it now compares the live container against `workloadRef.observedResources` — the values it recorded *before* the remediation, not `prePatchState`, which holds the persona's prior value and in the clean-room case was `512Mi`, a number the Deployment never had.

- **New condition on RemediationAction: `WorkloadDiverged`.** `True` with reason `WorkloadDiverged` when the live workload still carries the change, `False` with `WorkloadRestored` when it does not, `Unknown` with `WorkloadUnreadable` when Dorgu could not read it — an unreadable workload is not a restored one. Its message names the Deployment, the container, each field, live versus pre-remediation, and what to do about it, and is written to be printed verbatim by a client. An unmanaged workload gets the `kubectl set resources` invocation; every other owner, including `unknown`, gets the same owner-shaped instruction the plan itself would have used, because a rollback advisory is not an exemption from the ownership rule. The divergence is also logged with the deployment, container, `managedBy` and every diverged field.

- **A note appended to prose gets the full stop it was missing.** `appendNote` joined two sentences with a space, which is how "…1 applied on approval and 1 advisory Clamped by the 2x blast-radius guardrail…" reached the clean-room's screen. It also mattered mechanically: the CR5-01 scrub redacts by sentence, and a model sentence fused to a Dorgu-authored note could not be removed without taking the note with it.

## [0.11.1] - 2026-08-27

### Upgrade notes

> **Every operator image published before 0.11.1 was amd64-only.** `ghcr.io/dorgu-ai/dorgu-operator` up to and including `0.11.0` was pushed as a single-platform manifest rather than a manifest list. That covers AWS Graviton nodegroups and any local kind or k3d cluster on an Apple Silicon Mac. There is no workaround on an affected cluster other than upgrading: the arm64 image did not exist to be pulled.
>
> **The symptom on containerd is `exec format error`, not `ImagePullBackOff`.** This note originally said the pod stays in `ImagePullBackOff` with `no matching manifest for linux/arm64`, and clean-room run #5 measured otherwise on EKS 1.35 with containerd 2.2.5. With no manifest list to select from, containerd has nothing to reject: the pull **succeeds**, the amd64 binary is started on an arm64 kernel, and the container terminates immediately.
>
> ```
> Pulled   Successfully pulled image "ghcr.io/dorgu-ai/dorgu-operator:0.11.0" in 2.771s
> Started  Container started
> $ kubectl logs arch-probe-0110
> exec /manager: exec format error
> $ state: {"terminated":{"exitCode":255,"reason":"Error"}}
> ```
>
> So the pod reads `CrashLoopBackOff` with exit code 255. `ImagePullBackOff` with `no matching manifest for linux/arm64` is the Docker-daemon variant, which is what a `docker run` on a developer's machine produces and what this note described. The distinction matters because someone debugging on Graviton searches for the error they can see: "no matching manifest" returns nothing, and they never connect `exec format error` to the architecture of the image.
>
> **0.11.1 is that image and nothing else.** No API, CRD, controller or chart-template change, so the upgrade is a tag bump. If you pin the image by digest, repin to the manifest list digest rather than to either platform's manifest, otherwise a mixed-arch nodegroup will still fail on half its nodes.

### Fixed

- **The release workflow now publishes `linux/amd64` and `linux/arm64` as a manifest list.** The `docker/build-push-action` step carried no `platforms:` key, so it built one image for the runner's own architecture and pushed it as a plain `application/vnd.docker.distribution.manifest.v2+json`. Because `ubuntu-latest` is amd64, so was every image the project has ever shipped. The step now names both platforms, and `docker/setup-buildx-action` provides the docker-container driver, without which buildx cannot build more than one platform in a single invocation. `docker/setup-qemu-action` registers the binfmt handlers.

- **The Dockerfile cross-compiles instead of emulating.** The builder stage was `FROM golang:1.25` with no build platform pinned, which means a multi-platform build resolves the Go toolchain itself to the *target* architecture and runs it under QEMU. Measured on an arm64 host targeting amd64, the old stage reported `GOHOSTARCH=amd64`: an emulated compiler, correct in its output and needlessly slow in getting there. Pinning the stage to `--platform=${BUILDPLATFORM}` reports `GOHOSTARCH=arm64` with `GOARCH=amd64`, which is what cross-compilation looks like, and is available for free because the binary is already `CGO_ENABLED=0`. This was latent rather than harmful while only one platform was built, since build platform and target platform were the same one.

- **`make docker-buildx` builds the committed Dockerfile.** The kubebuilder scaffold `sed`-ed `--platform=${BUILDPLATFORM}` into a throwaway `Dockerfile.cross` at build time, precisely because the real Dockerfile lacked it. That made the local multi-arch target and release CI build different inputs, which is how the gap survived: the target that worked was not the one that shipped. The Dockerfile carries the pin now, so the generated copy is gone and both paths build the same file. `PLATFORMS` also drops `linux/s390x` and `linux/ppc64le`, which CI does not publish and nothing Dorgu targets runs on.

## [0.11.0] - 2026-08-27

### Upgrade notes

> **With `aiRemediation.enabled=true`, remediations become appliable again. Before this change they were not, and following the quickstart verbatim could not heal anything.** Clean-room run #4 measured it: 9 AI-planned remediations, 0 that could change a workload. The planner described the memory fix as `workload-apply` steps, which the CRD's CEL rule forbids from ever being `autoExecutable`, and gave the one `persona-update` step no patch at all. `spec.action.type` therefore came out `notification`, `dorgu remediation approve` printed "No resource change to apply", and the pod was still in CrashLoopBackOff 42 minutes later. Turning the planner off healed the identical app on the first try.
>
> **A number the model asked for may now be replaced by one Dorgu computed.** When a plan's persona-update step carries no usable patch, or carries one the blast-radius guardrail refuses, Dorgu fills in the value from the same deterministic calculation the rule-based path uses. The plan keeps the model's root cause; the number that reaches your cluster is the rule engine's. Every substitution is recorded on the step, so nothing about it has to be inferred from prose.
>
> **New optional CRD field: `spec.steps[].safety`.** A list of guardrail verdicts, each naming the field, what was requested, what is permitted, the ratio, the ceiling, and a ready-to-print message. Existing objects need no migration: the field is optional and absent means no guardrail ruled. CRD regenerated in `config/crd/bases` and mirrored into `charts/dorgu-operator/crds`. A CLI that does not know the field yet renders exactly as it does today.

### Added

- **`spec.steps[].safety`, a list of guardrail verdicts on a step.** Each entry carries `rule` (`blast-radius`, `plan-validation` or `absent-field`), `verdict` (`clamped`, `rejected` or `derived`), the `field`, the `baseline` it was measured against, what was `requested`, what is `permitted`, the `ratio` and `maxRatio`, and a Dorgu-authored `message`. Every string in it comes from Dorgu's own arithmetic, so a client can render it, filter on it or alert on it without parsing a sentence a model wrote.
- **F-05's "Dorgu will not introduce a field the workload lacks" is recorded structurally too,** as an `absent-field` entry beside the prose it already produced.
- **A guard test asserting the invariant across six adversarial plan shapes,** including the exact three-step plan the clean room recorded, and covering the case that must stay quiet: a diagnosis whose fix is not a resource change may be answered with advice alone.

### Fixed

- **An AI plan that diagnoses a resource change now always produces a `persona-update` step with a populated patch, or is not written at all.** Three separate holes fed the same outcome. The prompt let a container resource change be expressed as `workload-apply`, which is advisory by construction. `patch` was not required on a `persona-update` step, so the model could and did omit it. And nothing checked, before persisting, that the plan could do the thing it said it would. The fix is in that last place, because the first two are the model's behaviour and cannot be relied on: after the guardrails run, a plan for a diagnosed resource change either carries an appliable patch or Dorgu supplies one from `calculateResourceChange`, the rule engine's own conservative increase measured against the live workload. `assertAppliableWhenResourceDiagnosed` re-checks the invariant against the object immediately before the `Create`, so it holds regardless of what any future change does to the steps in between. A plan Dorgu cannot make appliable is refused and the rule-based proposal takes over, which records `planSource: rule-based` and is therefore auditable as what it is.
- **Dorgu fills in a step the plan already has; it does not invent one.** A plan containing no `persona-update` step did not propose a persona change at all, and grafting Dorgu's step into an AI-labelled plan would produce a plan no model wrote. That case falls back to rules wholesale.
- **The one exemption, and it is deliberate: when Dorgu's own rule engine declines to size a change, the advisory plan stands.** The live container setting no CPU limit means raising one would introduce a field the workload has never had (F-05), so the rule-based path would produce nothing either. An advisory plan that says exactly that is worth more than no plan, and it is not the defect above.
- **A `persona-update` step carrying no patch is now removed from the plan rather than displayed.** It applies nothing and it instructs nobody, since "update the ApplicationPersona" is Dorgu's own job, and it is what rendered as `(no changes)` under a plan that read like a fix. A step whose patch a guardrail emptied is kept, because it carries a record of which field was refused and why: that is the difference between a step that explains an absence and a step that is one.
- **A patch returned as a bare JSON object instead of a JSON-encoded string no longer throws the whole plan away.** The tool schema asks for a string, and decoding an object into that field failed the entire tool input, not the one field, so the plan was retried once, failed identically, and degraded to rules with the model's diagnosis discarded. Both shapes are now accepted, and an unusable value leaves the patch empty rather than failing the step around it.
- **The blast-radius verdict is structured data, not a prefix on the model's prose.** It used to be spliced onto the front of `rationale` as `[safety:blast-radius] …`, so a computed refusal read as part of the model's reasoning, one line below the model's own claim that the same 16x change was "well within a 2x ceiling". The verdict now lives in `spec.steps[].safety`, and Dorgu writes the step's description and rationale on any step a guardrail has touched. The model is no longer in a position to characterise a verdict that was never its to give, and the prompt now forbids it from commenting on caps at all.
- **A refused field is removed from the step's patch, so nothing can advertise a change that will not happen.** Previously the patch kept the refused value while the step was demoted to advisory, and the diff block went on offering `8Mi -> 128Mi` to a reader who would have got nothing. Where Dorgu can substitute a permitted value the patch carries that instead, and the diff shows what will actually happen.
- **The owner instruction is built after the guardrails, not before.** It quotes concrete values out of the plan's patches, so building it first told a Helm user to put the refused value in their values file. This was the same defect as the one above, one screen further down, and was caught by moving the code.
- **`checkBlastRadius` reports every field that breaches the cap, in a stable order.** It returned the first breach it happened across while ranging over a map, so a plan moving two fields too far had one named at random and the other silently ignored.

- **Resource saturation no longer counts pods no node has accepted.** `ClusterPersona.status.resourceSummary.cpuUtilization` read **1689%** on a cluster where 25% was requested and 1% was in use. `setClaimedResources` skipped terminal pods and nothing else, so pods sitting in the scheduling queue had their requests summed against node allocatable. That is not an over-estimate to be tightened: an unscheduled pod holds no allocation on any node, and because such a pod can request more than the cluster owns, the error has no upper bound.

  Only pods a node has actually accepted are counted now. `podHoldsAllocation` makes both exclusions explicit and says why they differ: a Succeeded or Failed pod ran to completion and released its allocation, while a pod with an empty `spec.nodeName` never had one, whether nothing can fit it, it is waiting on a node that has not joined, or it is gated.

  ```
  before: usedCPU 63965m / allocatable 3860m  ->  cpuUtilization 1657%
  after:  usedCPU   965m / allocatable 3860m  ->  cpuUtilization   25%
  ```

  A Pending pod that *has* been bound to a node still counts, because a reservation held while an image pulls is a real reservation. This field feeds the dashboard's cluster view, where a wrong number reads as authoritative in a way terminal output does not; the CLI stopped depending on it in the same fix set (the paired CLI release computes saturation itself from nodes and pods), so the two are corrected from both ends.

  Worth noting: the CRD's own description of `usedCPU` already said "the CPU claimed by the resource requests of **scheduled** pods". The schema was right and the code did not match it.

### Known limitation

- **The 2x cap still anchors to the live value, so an app that has drifted far below its recorded intent cannot be restored in one step.** After a drift down to 8Mi the largest permitted step is 16Mi, which may still be too little. Dorgu now says so in the step's verdict and in the plan summary rather than implying the fix is complete, but the anchor itself is unchanged: moving it to the persona's recorded intent would weaken the guardrail in exactly the case where the persona is the thing that is stale.

## [0.10.0] - 2026-08-25

### Upgrade notes

> **1. Incidents now stay open roughly 6 minutes longer in the happy case. This is deliberate: silence is not recovery.** Resolution used to need two absences, no matching signal this cycle and 5 minutes since the last one. A pod deep in CrashLoopBackOff emits nothing while it backs off, which is precisely when an incident used to close. Resolution now additionally requires an observed stable window: pods present, Ready, and continuously Ready for `RecoveryStabilityWindow` (**6 minutes**, chosen to exceed the 5-minute maximum CrashLoopBackOff interval), with no container restart or return to a waiting state inside it. The added latency is the price of not calling a dead pod healthy. There is no flag to opt out.
>
> **2. AI model calls now scale with the number of simultaneously broken applications.** Diagnosis used to run once per signal type across the whole cluster, which was the defect rather than an optimisation: four broken apps produced one diagnosis and therefore one incident. It now runs once per broken application per cycle, so four broken apps cost four diagnoses per cycle where they previously cost one. **Worth knowing if you supply your own key.** This is inherent to the fix, because a per-application diagnosis cannot come out of a single cluster-wide call.
>
> **3. The manager ClusterRole gains exactly one verb: `delete` on `dorguevents.dorgu.io`.** Nothing else widened. The grant is scoped to Dorgu's own CRD and to no workload kind, so the published claim that the operator never writes your workloads is unchanged. A test now asserts the operator still cannot `create`, `update`, `patch` or `delete` Deployments, ReplicaSets, Pods, Nodes or Namespaces. Check it on a live cluster rather than taking it on trust:
>
> ```
> kubectl auth can-i delete dorguevents.dorgu.io --as=system:serviceaccount:dorgu-system:dorgu-operator -A   # yes
> kubectl auth can-i delete deployments          --as=system:serviceaccount:dorgu-system:dorgu-operator -A   # no
> ```
>
> **Existing `IncidentMemory` objects need no migration.** `spec.attribution` is a new optional enum, and an empty value reads as persona-attributed, which is what every pre-upgrade incident was. The field and its label are backfilled on first touch, so no duplicate incidents are raised across the upgrade. The CLI needs no change either: an unattributed incident's `personaRef.name` is the workload name and renders normally.

### Changed

- **An incident is resolved only on positive evidence of recovery, never on the absence of a signal.** `resolveCleared` used to need two absences: no matching signal this cycle, and 5 minutes since the last one. Silence now only opens the question, and `verifyRecovery` has to answer it with an observation. Pods must exist, be Ready, have been Ready for the 6-minute stability window, and have no container that restarted or re-entered a waiting state inside that window. The verdict is three-valued rather than two: a terminating or completed pod says nothing and counts as neither evidence nor a blocker, so a resolution needs at least one pod actually confirmed healthy and an all-terminating set is not a vacuous "all pods Ready". Zero pods is not recovery by default; it falls through to the workload, where no Deployment at all or a Deployment scaled to zero resolves as `workload no longer running`, while a Deployment that wants replicas and has none stays open. Any error reading the cluster leaves the incident open, because not knowing is not recovery. The reason is written to `spec.resolution.action`, so why an incident closed lives on the object rather than only in a log line that will rotate. A Failed or evicted pod matching the workload holds its incident open until it is garbage-collected, deliberately, under prefer-open-to-wrongly-closed; the reason names the pod so it is actionable. This was reported as `platform/checkout` reaching 51 occurrences and then going `Resolved` while still crash-looping.
- **Diagnosis is partitioned by application, so one incident can no longer span several.** `diagnoseOOM` and `diagnoseCrashLoop` took *all* signals of a type as a single finding, named `firstPersonaRef` as the owner, and listed every affected pod, so four broken apps in three namespaces collapsed into one incident owned by whichever persona sorted first. A new `detection.GroupSignals` partitions signals into per-persona, per-unattributed-workload and cluster-scoped groups **before** diagnosis, so a rule can only ever see one application's signals and therefore can only ever describe one application. This is also the upstream cause of the invented cluster-wide root causes: given every pod eviction in the cluster as one finding, the model reasonably reported cluster-wide memory pressure on nodes that were sitting at 23%. Pinned by `TestReconcile_Acceptance_FourBrokenAppsAreFourIncidents`, which puts 4 broken apps in 3 namespaces through the real collector, correlator and rules and requires 4 incidents.
- **Mass resolution had the same root cause and is fixed by the same change.** Because only one diagnosis existed per signal type, only one entry landed in `activeSignalKeys`, so the other applications' incidents matched nothing that cycle and aged out through the grace period. Reported as a separate defect; it was a symptom of the bundling above.
- **A foreign `Update`-operation field manager that owns a container's `resources` block now counts as ownership.** The classifier counted `Apply`-operation managers only, on the stated premise that an `Update` entry (what `kubectl patch` and `kubectl set` produce) claims no ongoing ownership and so predicts nothing about a future conflict. That premise is false, and was reproduced against kube-apiserver 1.36.2: server-side apply conflicts with whoever owns the field, however they came to own it. `unrecognisedApplier` is replaced by `foreignFieldOwner`, which counts any foreign `Apply` entry (unchanged) plus a foreign `Update` entry owning the exact field set a remediation writes. The check reads `managedFields[].fieldsV1` rather than treating any foreign `Update` as ownership, because without that scoping every cluster running KEDA, an HPA-alike or a sidecar injector would classify as owned and Dorgu would refuse to heal anything: a manager holding only `spec.replicas` or a pod-template annotation is not in the way of a resource patch. `kubectl-*` managers stay excluded on purpose, so a Deployment carrying `kubectl-set:Update` on the target fields still reads `unmanaged` and is still healed. That is a human with kubectl, which is the definition of unmanaged, and healing there leaves the user better off: the `Update` moves the claim onto `dorgu` and the CLI then drops it, clearing a pre-existing conflict instead of adding one.
- **A refusal on an unknown owner names the field manager it refused on behalf of,** in both the plan step and the owner instruction. "Dorgu could not identify what manages this Deployment" is a dead end. The manager's name is a lead.
- **The `DorguEvent` cleaner's batch size is raised from 50 to 200, and it runs one pass at startup** instead of waiting a full interval. 50 records per 30 minutes barely exceeded the arrival rate, so the backlog never drained, and a restarted operator inherits the largest backlog it will ever see.

### Added

- **Unattributed incidents, for workloads no persona claims.** A broken Deployment with no matching ApplicationPersona used to be folded into a neighbouring application's incident, which is how one app got blamed for another's outage. It now gets its own incident recorded against the workload, carrying `spec.attribution: unattributed` and a `dorgu.io/attribution` label. The root cause says plainly that no persona claims it and points at `dorgu persona import`. No remediation is proposed for it and no persona status is synced, since there is no persona to sync. An unattributed incident hands over to an attributed one only when the attributed incident already exists and is open, so onboarding an app in the middle of an outage never leaves it with no incident at all.
- **`spec.attribution` on `IncidentMemory`,** a new optional enum of `persona` or `unattributed`. CRD regenerated in `config/crd/bases` and mirrored into `charts/dorgu-operator/crds`.
- **`DorguEvent` records are now bounded by count as well as age.** `dorguEvents.maxRecords` (default **2000**, `--dorgu-event-max-records`) prunes oldest first once the cap is exceeded, and `dorguEvents.retention` (default **24h**, `--dorgu-event-retention`) is the age bound, plumbed into both the writer and the cleaner so a record states the retention the operator is actually running with. A TTL alone bounded nothing: records arrive in proportion to cluster size, so five apps producing 187 records in 100 minutes were all inside the 24-hour window and all in etcd. Set `maxRecords: 0` to keep retention as the only bound.
- **`delete` on `dorguevents.dorgu.io` in the manager ClusterRole.** The cleaner existed but had no permission to act, so every cycle logged a failure and nothing was ever removed. The grant is scoped to Dorgu's own CRD and to no workload kind, so the published claim that the operator never writes workloads is unchanged; two tests now hold that line, one asserting the new verb and one asserting the operator still cannot create, update, patch or delete Deployments, ReplicaSets, Pods, Nodes or Namespaces. Verify it yourself rather than take it on trust: `kubectl auth can-i delete dorguevents.dorgu.io --as=system:serviceaccount:dorgu-system:dorgu-operator -A` says yes, the same question about `deployments` says no.

### Fixed

- **Signal attribution now requires exactly one persona.** Personas `api` and `api-server` both claim pod `api-server-7f9d-x2q`. The more specific claim now wins, and a genuine tie is left unattributed rather than decided by API list order. The correlator never crosses namespaces.
- **Diagnoses were dropped on a `NotFound` race rather than a `Conflict` one.** `retryIncidentWrite` now retries on both, with a backoff tuned for cache lag (6 steps to about 1.5s) instead of for optimistic concurrency (`retry.DefaultRetry` gives up in about 50ms). The status write straight after `Create` no longer re-reads on the first attempt, because the object returned by `Create` already carries a valid ResourceVersion and the unconditional `Get` was what exposed the write to a cache that had not caught up. `AlreadyExists` on create now adopts the existing incident and folds the diagnosis into it instead of returning an error and discarding a paid-for analysis. The rule from v0.9.0 is intact: a genuinely lost diagnosis is still ERROR plus a `DorguDiagnosisDiscarded` event plus a `DorguEvent`, never silently dropped.
- **kustomize detection never fired on kustomize's own output.** Confirmed against kustomize v5.8.1 as shipped in kubectl. The only marker kustomize generates itself is opt-in `buildMetadata: [managedByLabel]`, and it writes `app.kubernetes.io/managed-by: kustomize-v5.8.1`, which is **versioned**, so the old exact match on `kustomize` could only ever match a value a user hand-wrote into `commonLabels`. The managed-by label is now matched by prefix, and the two other opt-in build-metadata markers (`config.kubernetes.io/origin` and `alpha.config.kubernetes.io/transformations`) are recognised. The honest limit is now stated in the code and pinned by a test: **a plain overlay is undetectable and reads `unmanaged`.** kustomize emits no label and no annotation by default, and `kubectl apply -k` records the same `kubectl-client-side-apply:Update` manager as `kubectl apply -f`, because kustomize is a client-side renderer with no controller. There is nothing to detect, by design.
- **171 of 188 ERROR lines in a 20-minute window came from a write that had already succeeded.** `DorguEvent` names are content-addressed, the event informer re-lists everything it holds on each resync, and the resync period was the same 5 minutes as the store's dedup window, so a settled event came back round just as its dedup entry expired and the `Create` returned `AlreadyExists`. That is idempotent and is now handled as such, at `V(1)`. The store also stopped logging the error it returns: every caller already logged it, so each real failure was printed twice, at two layers.
- **A duplicate record aborted the pipeline before the emit step.** Because the benign `AlreadyExists` came back as an error, `processEvent` returned on it and the Kubernetes Event was never emitted. Nine ERROR lines a minute on a five-app cluster is enough to make log-based alerting useless on day one, and the docs point that alerting at `DorguDiagnosisDiscarded`, so the noise was breaking the mechanism it was reported through.
- **An event's reason is now part of what identifies it.** Neither the dedup key nor the record name included the Kubernetes Event reason, so two unrelated things happening to one object inside one category were the same event and the second was dropped. On an `IncidentMemory` that meant an ordinary health event could swallow the `DorguDiagnosisDiscarded` record users are told to alert on. Event times have second granularity, so same-second collisions between distinct reasons were losing real records too.
- **The event pipeline no longer observes its own output.** The emitter writes a Kubernetes Event for every record it stores, the watcher then saw that Event and stored a second `DorguEvent` saying Dorgu had said something. `DorguDetected` and `DorguDiagnosisDiscarded` accounted for 24 of the duplicate-key errors and every one of those records was an echo. Nothing is lost by dropping them: the Kubernetes Event alerting selects on is still emitted, and the reconciler writes its own `DorguEvent` directly.

## [0.9.0] - 2026-08-23

### Upgrade notes

> **Remediations for workloads owned by Helm, ArgoCD, Flux or kustomize are now recommendation-only. Dorgu will not patch them.** The operator observes the live Deployment, records who owns it, and shapes the plan as instructions for that owner's source of truth instead of a command that writes to the cluster.
>
> This is deliberate. Patching a Deployment that Helm or ArgoCD reconciles claims the fields Dorgu writes, and the next `helm upgrade` then fails outright with a field-manager conflict rather than quietly reverting the fix. A fix that breaks your next deploy is not a fix. Clean-room run #2 hit exactly that.
>
> **What is unchanged:** `persona-update` steps still patch the ApplicationPersona, the operator still does that itself, and ownership has no bearing on it. Their `autoExecutable` semantics are the same as before. Only the write to the Deployment is gated, and only `managedBy: unmanaged` permits it.
>
> **`unknown` is treated as owned.** Where the Deployment cannot be resolved, or its server-side applier is not one Dorgu recognises, `managedBy` is `unknown` and Dorgu explains rather than writes. Nothing is patched on a guess. One consequence worth knowing: a workload the operator cannot resolve loses its advisory `kubectl` commands too, so resolution failures now cost plan usefulness as well as grounding.
>
> **This guard is enforced by the CLI, so upgrade both.** The operator supplies the facts in `spec.workloadRef` and strips the workload-writing commands; refusing the patch is `dorgu remediation heal`'s job. **CLI v0.9.0 and older do not read `workloadRef` at all** and will still patch an owned Deployment on approval. Pair this release with **CLI v0.10.0 or newer**.

### Changed

- **Remediations are grounded in the live workload rather than the persona.** The ApplicationPersona is a point-in-time import, and in a brownfield cluster it drifts from the running Deployment. Dorgu previously computed sizes, stated numbers, and diffed as though the persona were authoritative, so it would quote a memory limit the container had not had for weeks. Every stated fact and every cap now comes from the live container: the rule-based proposer sizes increases off the live limit, the explanation quotes only observed values and names the Deployment and container they were read from, and where the workload is unreadable it says so and warns that the persona figure may have drifted.
- **The blast-radius cap is measured against the live value, not the higher of the two.** Capping against `max(persona, live)` still permits a 192Mi proposal on a 32Mi container whenever the persona is the stale, larger number, which was the reported case. The cap is now strictly relative to what the container actually runs with. An action's `prePatchState` still records the persona's prior value, because that is what a persona rollback restores.
- **Dorgu no longer proposes resource keys the workload does not have.** `observedResources` distinguishes absent from zero, so approving a memory fix can no longer silently introduce a CPU limit the Deployment never set. The rule-based path refuses to raise a limit the container does not set and says why; the AI path drops any patch leaf targeting a missing key, records the omission in the step rationale, and demotes a step whose patch is emptied by that pruning.
- **Plans are shaped for whoever owns the workload.** For an owned Deployment, every step whose command writes to the cluster loses that command and is rewritten as what to change at the source: chart values for a Helm release (hedged as chart-specific, because Dorgu has not read the chart), the Git manifests for an ArgoCD application, the Git source for a Flux resource, the kustomize overlay. Each carries one line on what a direct patch would have broken. Read-only commands such as `kubectl logs` and `kubectl get events` survive, because they matter most on the workloads Dorgu will not touch. An `unmanaged` workload keeps its direct `kubectl` command exactly as planned.
- **The AI planner prompt leads with ground truth.** A new `## Live workload (ground truth)` section sits ahead of the persona, which is now explicitly labelled a stale snapshot, followed by six grounding rules and six ownership rules. The only image versions the model may name are ones Dorgu has actually read, from the `dorgu.io/imported-image` annotation and `status.deployments`, so it can no longer invent a prior-good tag.

### Added

- **`spec.workloadRef` on `RemediationAction`,** populated by the operator at proposal time from the live Deployment. It carries `kind`, `name`, `namespace` and `container` (the live object's name, which in a brownfield cluster is usually not the persona name: persona `frontend` resolving to Deployment `frontend-podinfo`), the observed `resources` requests and limits where an empty string means the workload does not set that key, plus `observedImage` and `observedAt`.
- **`workloadRef.managedBy`,** one of `helm`, `argocd`, `flux`, `kustomize`, `unmanaged` or `unknown`, defaulting to `unknown`. It is derived from server-side-apply field managers plus labels and annotations, most specific owner first: ArgoCD, then Flux, then Helm, then kustomize. A Flux HelmRelease reads as `flux` rather than `helm`, because Flux is what reconciles it. Update-operation field managers, which is what `kubectl patch` and `kubectl set` leave behind, claim no ongoing ownership and so read as `unmanaged`. `managedByDetail` names the specific owner in prose, for example `Helm release "frontend" in namespace apps`, so a refusal can name what owns the workload instead of saying that something does.

### Fixed

- **176 AI diagnoses were silently discarded on write conflicts.** `updateExistingIncident` mutated the `IncidentMemory` it got from a `List` and called a bare `Update`, so that snapshot's ResourceVersion lost to any concurrent write and the whole diagnosis went out with the error. The status write beside it had been given `retry.RetryOnConflict` earlier; the spec write never was, and the spec write is the one carrying the AI root cause, which is why the diagnoses being dropped were the better ones. The spec write now retries with a re-fetch and re-applies the diagnosis to the fresh object, and `createIncident`'s initial status write got the same treatment, since a conflict there left an incident created but statusless with its diagnosis gone.
- **Losing a diagnosis is now visible instead of silent.** Nothing counted the losses, which is why 176 of them across 4h20m only surfaced by grepping raw logs. Exhausted retries now log at ERROR, record a `DorguEvent`, and emit a Kubernetes Warning on the incident under the new reason `DorguDiagnosisDiscarded`, so the loss shows up in `kubectl get events`, in `dorgu health`, and to log-based alerting. Every cycle ends with a tally: a cycle that lost work says so at ERROR, a clean one stays at `V(1)`.
- **Rejecting a remediation re-proposed the same fix 30 seconds later.** `Rejected` counted as terminal and therefore non-blocking, so the next health-check cycle proposed again, and `dorgu remediation reject` patched only `status.phase`, leaving no timestamp to hold a cooldown against. The remediation controller now stamps a `Rejected` condition once, on first sight of the phase, so re-reconciling cannot restart the clock. The health-check reconciler consults that history before calling the proposer, which puts the suppression ahead of any billable planning call. Suppression is scoped to the incident and its target and lifts after **1 hour** or when the signal materially changes, meaning the live diagnosis outranks the severity the declined incident was opened at: a warning someone waved off that has since gone critical is a different question. An unreadable rejection history fails closed, and a rejection with no timestamp yet still suppresses, because an un-timestamped no is still a no.
- **The release rehearsal deleted a tracked file.** The step 8 rehearsal packaged the chart into `dist/`, mirroring release CI, but `dist/install.yaml` is committed in this repo, so cleaning up with `rm -rf dist` removed it and it had to be restored before the release commit. The rehearsal now packages into `/tmp/dorgu-release`, with a comment recording why it differs from CI, and gained a step that renders the packaged chart's `NOTES.txt` before tagging: the notes are the one artifact no test sees until publish, since `helm template` cannot render them at all.

### Fixed

- **The AI diagnosis you paid for now reaches the incident record.** The operator logged `{"provider": "ai-enhanced", "count": 2}` while `grep -c ai-enhanced` across every `IncidentMemory` returned **0**: every incident read `Provider: rule-based`, `Confidence: 70%`. The cause was the diagnosis engine's "higher confidence wins" merge. `AIProvider` re-runs the rule-based logic and applies the LLM's `ConfidenceAdjustment`, which no response parser populates, so an AI-enhanced diagnosis carries the rule-based confidence *to the digit*. Under a strict `>` comparison over a provider list that starts with the rule-based provider, the AI result lost every tie and was dropped without a word. Ties now go to the later provider (the one enhancing the earlier result), the losing diagnosis is logged at INFO with the reason, and `updateExistingIncident` refreshes the root cause at equal confidence so an incident first recorded before AI was configured is upgraded rather than frozen as `rule-based`.
- **Approving an advisory remediation no longer fails it and blacks out the app for 30 minutes.** Dorgu proposed a `notification`-type remediation, printed its own approve command, and approving it produced `apply failed: precondition failed: unsupported action type "notification"`, phase `Failed`, and then `[rate-limit] failed remediation ... within 30m0s cooldown period`. An approved plan with nothing to apply now settles as **`Acknowledged`**: the approval is recorded, the operator changes nothing, and the incident is marked `acknowledged` (not resolved, because nothing was fixed). Separately, a plan the executor refuses before touching the cluster is recorded as `PreconditionRejected` and is **excluded from the failure cooldown**, which now only counts remediations that actually went wrong.
- **Dorgu's Kubernetes Events are recorded again.** Every event was dropped by client-go with `"Could not construct reference, will not report event" err="object does not implement the common interface for accessing the SelfLink"` (77 of them in one clean-room run), so `kubectl get events --field-selector reason=DorguDetected` returned nothing and anyone reading the operator log saw a wall of ERRORs. The emitter passed a hand-rolled `runtime.Object` carrying only a GVK, a name and a namespace; it now passes a `corev1.ObjectReference` with the apiVersion filled in for the kinds dorgu attaches events to. An event whose involved object has no kind or no name is refused with an error instead of being emitted into the void. `record.FakeRecorder` ignores the object it is handed, which is why the old tests passed: the new ones resolve the reference the way the real recorder does and assert the `Event` object is created through a real broadcaster and sink.
- **Cluster resource saturation is actually computed.** `usedCPU`, `usedMemory`, `cpuUtilization` and `memoryUtilization` were declared on `ClusterPersona.status.resourceSummary` and never written by anything, which is why `dorgu health` printed `CPU: n/a requests / allocatable ( / 3860m)` with an empty left operand on every cluster. They are now totalled from the resource requests of scheduled pods (sum of app containers, floored by the largest init container, terminal pods excluded), matching what the CLI renders as "requests / allocatable". Requests rather than live metrics deliberately: no metrics-server needed, so the figure is there on a default install. Utilization is left empty rather than reported as `0%` when allocatable is unknown.
- **A fix clamped by the 2x guardrail says so.** `report-worker` needed ~120M; the plan proposed 48Mi to 96Mi at confidence **0.88** with a summary asserting it resolves the OOM, and the pod went straight back to `OOMKilled`. 96Mi was not a judgement, it was the ceiling. When a proposed value lands at the blast-radius cap, the plan summary, the explanation and the step rationale now say "Clamped by the 2x blast-radius guardrail: ... may be insufficient and a second increase may be required", and the confidence is damped by 0.15 (0.88 becomes 0.75). This applies to both the rule-based proposer (where a critical OOM is capped at 2x in code) and the AI planner (whose prompt asks for changes within ~2x).
- Resolve an `ApplicationPersona` to its `Deployment` without requiring a label on the Deployment object. Helm, kustomize and most hand-written YAML label the pod template only, so personas for pre-existing apps sat `Pending` forever with `No Deployment with label app.kubernetes.io/name=<app>`. Resolution now walks an ordered chain: `app.kubernetes.io/name` label, `app` label, `metadata.name`, then `spec.selector.matchLabels`. When several Deployments match the same rung the persona reports `AmbiguousDeployment` and names the candidates instead of patching one at random; when none match, the message lists every rung that was tried.
- Validating webhook checks Deployments labelled on the pod template only, instead of exempting them with "no app.kubernetes.io/name label; skipping persona validation".

## [0.7.3] - 2026-08-07

### Upgrade note

> **Clusters running `selfHealing.mode: observe` will stop receiving remediation proposals after this upgrade.** The mode is now enforced (see below). Before 0.7.3 the field was inert, so an `observe` cluster still got `RemediationAction`s. Bootstrap versions before 0.7.3 hardcoded `mode: observe` on the auto-created `dorgu-cluster` persona, so most existing clusters are in exactly this state. Upgrading is safe but silent: detection and diagnosis keep running and `IncidentMemory` records keep appearing, while zero remediations are proposed.
>
> Check the current mode and restore the previous behavior with:
>
> ```bash
> kubectl get clusterpersona dorgu-cluster -o jsonpath='{.spec.policies.selfHealing.mode}'
> kubectl patch clusterpersona dorgu-cluster --type=merge \
>   -p '{"spec":{"policies":{"selfHealing":{"mode":"propose"}}}}'
> ```
>
> New installs are unaffected: the bootstrap and the CRD default both use `propose`. If a persona was created by a clone install of the 0.7.2 chart, its `mode` may have been pruned entirely (the bundled `ClusterPersona` CRD was missing `policies.selfHealing`), in which case the CRD default `propose` applies once the 0.7.3 CRDs are installed.

### Fixed

- **`selfHealing.mode: observe` is now enforced — the safety switch works** — the CRD advertised `observe | propose | auto-approve`, but no code branched on the mode: `observe` still created `RemediationAction`s, so the API made a safety promise it did not keep. The proposer now honors `spec.policies.selfHealing.mode` from the `ClusterPersona` before doing any work: **`observe`** detects, diagnoses, and records an `IncidentMemory` but creates **zero** `RemediationAction`s, logging `selfHealing.mode=observe — proposal suppressed` with a hint for switching to `propose`; **`propose`** (the default) keeps the existing behavior; **`auto-approve`** is **not implemented** and is accepted but degraded to `propose` with a prominent warning rather than silently auto-approving — approval is always required today. An unrecognized mode is treated as `propose` and logged. The gate runs ahead of the AI planner, so `observe` spends no API calls. The auto-created `dorgu-cluster` persona and the controller's default-fill now use `propose`, matching the CRD's kubebuilder default — they previously said `observe`, which would have suppressed every remediation out of the box once the mode was enforced. `approval.autoApproveRule` and `selfHealing.enabled` are marked **not yet implemented** on the Go types and in the CRD schema so they stop reading as promises.
- **`helm install ./charts/dorgu-operator` from a clone installed the wrong image and an incomplete CRD set** — release CI restamps `Chart.yaml` from the git tag at publish time, so the committed `version`/`appVersion` sat at `0.6.1` even at tag `v0.7.2`; since `templates/deployment.yaml` defaults the image tag to `appVersion`, a contributor install ran the **0.6.1 image — an operator with no AI planner**. The bundled `crds/` had drifted the same way: only **2 of 5** CRDs were committed, and the `ClusterPersona` CRD was missing the whole `policies.selfHealing` block, so a clone install silently pruned `mode`, `excludeNamespaces`, and `maxRemediationsPerHour`, and could not create `IncidentMemory`, `RemediationAction`, or `DorguEvent` at all. `Chart.yaml` is now pinned to `0.7.2`, all five CRDs are synced from `config/crd/bases`, and two chart tests guard both invariants: `appVersion` may not lag the latest git tag, and the bundled CRDs must match the generated ones byte for byte. `/release` gained an explicit chart-bump step. Published OCI installs were never affected.
